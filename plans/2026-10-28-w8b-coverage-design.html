Recommendation and summary

Recommendation: do not start W8b by "adding a heartbeat". Implement it as a producer-attested, receiver-verified commit-sequence proof whose only claim is about successful admitted evaluation completions (scope eval_completions). Build the verifier before the prover: pure model → receiver → producer evidence → checkpoint dispatch → optional cron activation → drills → human-gated rollout. Upstream product submissions, front-door outages and "no school activity" are not provable from this repository; they need a separate authoritative integration (below). A verified zero means "the producer's gapless completion ledger shows zero commits for a fully observed window", never "no students were active".

Why this design (evidence-led)

  • Observed IdempotencyStore.complete() has exactly one call site and the evaluation result is returned only after it resolves (app.ts:302-323 @222ee45). It runs in one per-tenant Durable Object inside one transactionSync (store.ts:217). That is a natural serialization point for a gapless per-stream sequence.
  • Observed Today the unit has silent holes: five return null paths in prepareTelemetryDelivery leave no row, no gap, no trace (O2). Any completeness proof must first make every completion classifiable.
  • Observed Receiver coverage fields are hard-coded "unavailable"; provisional is a clock heuristic, not evidence (O9).

What the proof can and cannot say

  • Proposed Can: complete non-zero count, verified zero completions, incomplete (with reason class), unobserved, provisional, not expected, withdrawn.
  • Proposed Cannot: distinguish "no demand" from "front door down / auth rejected / rate limited / evaluation failed" (no commit exists in any of those). Labelled completed_evaluations, never "activity".
  • Proposed Cannot: detect a receiver-storage rollback or a compromised writer key. Trust model is benign-failure, not adversarial producer.

Minimum extra authoritative integration for any activity or availability claim

Proposed A second, separately-scoped stream product_submissions: a durable, gapless, product-side counter (EducateOS / PlayTrek own the chokepoint where a student submission is created) per (source, 15-minute UTC bucket, grade band), carried by the same checkpoint algebra with its own streams, epochs and fence, plus a district-approved exposure inventory for expected-nonzero windows. Only then can "submitted but never evaluated" or "no submissions" be stated. Optionally a cheap in-repo precursor, eval_attempts (a ledger of begin() starts in the same DO), would expose evaluations that started and never completed; it is not W8b and not part of this proposal. No estimate of activity or human staffing is permitted by any of these.

Non-claims. Nothing here is implemented, run or tested. The existing suite (552 tests / 41 files and 84 drill checks, quoted from the task brief, not re-run) says nothing about this design. No retention duration, privacy or legal approval, dashboard, suppression rule, tenant enrolment or deployment is claimed or implied. Every number named below (fence, tick, caps) is a parameter to be measured and approved, not a recommendation.

A · Proof unit, trust and states Proposed

Observation scope

  • Scope id eval_completions. Unit: one completion commit by the tenant's IdempotencyStore (one per evaluation that returned a result through complete(); O1, O4). E and F in the receiver are projections of these commits (O17).
  • Out of scope (separate coverage scopes, each with its own proof): product_submissions (upstream), reports/cases (R, I, Q, V, P, C are different units per temporal-metrics.md:9-18), eval_attempts.
  • Declared outage semantics (answers brief A):
    • Worker / DO / front-door outage, auth rejection, rate limit, evaluation failure: not observable in this scope (no commit exists). A verified zero can coexist with an outage and must carry the label "completed evaluations".
    • Uninstrumented completion (old Worker version after a deploy, rollback below the W8b revision): observable if the Worker still emits v2 to a coverage-mode tenant (receiver taints the hour, see compat table) or if the optional receipts witness is built (the receipts table is written by every complete() of any code version, so a count of receipt rows with no matching ledger entry inside a window would expose an uninstrumented commit; store.ts:225-230); otherwise must remain unavailable and rollback below the W8b revision is an operational gate. Unverified receipts witness: JSON1 availability for recordedAt, and receipt TTL (HM_RETENTION_SECONDS, default 24 h) at least as long as the seal delay.
    • Invalid or absent coverage/enrolment/retention setting, or a disabled interval: observable only when traffic occurs (each completion records a disabled range while a stream exists); with zero traffic it is correctly a non-observation, never a zero, because no checkpoint is emitted while disarmed.

Proof objects (definitions)

  • Commit time of a completion = the producer logical clock inside the completion transaction. Fence F: a delivery is produced only if |commit time − occurredAt| ≤ F; otherwise the completion consumes its seq as a fence range (taints its occurrence hour and its commit hour). So any completion with occurrence in bucket b has commit time in [b.start − F, b.end + F].
  • Accounted frontier (through, seq): seq is the largest S such that every seq ≤ S is either acked (row deleted on a verified durable ack) or inside a producer range, and S's commit time ≤ through. Consequence (head-of-line blocking): one delivery still retrying holds the frontier, so buckets stay provisional for up to the retry horizon (6 h default, 12 h cap) before the row becomes a range.
  • Armed chain: consecutive armed observations (completions or ticks) no more than maxTickGapSeconds apart with no off observation between; armedSince is its start. Anything before armedSince is never claimed.
  • Presence: the receiver holds a (epoch, seq) for every seq in a claimed interval, or a range covers it. The receiver tracks a contiguous watermark verified_n (highest N with every seq ≤ N present or covered), advanced inside the delivery and checkpoint transactions, so verification does not depend on old dedupe rows surviving.
  • Verified span: a checkpoint that passes presence, merged into (armedSince, through, seq). Bucket b is sealable iff armedSince ≤ b.start − F, b.end + F ≤ through, no range overlaps b's hour, and no taint remains.
  • Producer values are never trusted as counts. A checkpoint carries only a frontier and declared losses, both derived from durable DO state in one synchronous pass. E and F always come from the receiver's own rollups; the checkpoint can only qualify them. A lying producer can make data less complete; it can make it complete only by also forging matching deliveries, which needs the writer key (out of scope, X7).

B · Durable evidence: designs compared Proposed

A · Commit-sequence progress with verified checkpoints Recommended

  • Gapless (epoch, seq) per stream, assigned in the completion transaction; carried as signed transport attributes.
  • Every seq is accounted: acked, or in a producer range (gap/unobserved).
  • Checkpoint = accounted(through, seq), armedSince, unreported ranges. Receiver verifies presence of every seq in the claimed range, then merges a span.
  • Detects loss, duplicates, forged/foreign seqs, restore/regression, epoch overlap.
  • Cost: new signed attributes (v3 route), seq index on the existing dedupe row, ~3 receiver tables, alarm ticks.

B · Durable per-bucket inventory reconciliation

  • Producer keeps per-bucket×dims commit counters in the completion transaction; checkpoints send counts for closed buckets; receiver compares equality.
  • No wire change to deliveries; naturally idempotent and order-free.
  • Weaker: equality can hold with a duplicate-ID delivery masking a loss; cannot see a restore that forgot earlier commits; per-bucket×dims counts in every checkpoint are large; epochs are invisible to the receiver's rollups (cannot attribute a mismatch to an epoch).
  • Useful later as defence in depth, not as the proof.

C · Heartbeat / silence detection

  • Receiver notes the last contact; "healthy" if recent.
  • Proves nothing about completions, retroactively blesses outages, cannot find lost deliveries (naive table above).
  • Rejected.

D · Upstream product submission counters

  • The only way to claim "no submissions" or "evaluation failed to run".
  • Requires EducateOS/PlayTrek code and agreements outside this repo.
  • Separate scope (product_submissions); the same algebra applies.

Times that reach storage are on the 15-minute grid and rounded in the conservative direction, so neither a sub-bucket commit time nor a precise completion rate is retained (consistent with retention.ts:41-47). Range reason is a closed enum: capacity expired revoked error conflict (existing W6 reasons), plus disabled unprojectable grant_mismatch fence coalesced from the producer and, receiver-derived only, legacy_v2 inconsistent seq_conflict regression overlap. disabled covers the v2 flag off, no collector binding, an absent or invalid grant, and an invalid coverage setting while a stream exists. A retention policy that is not in force is recorded as disabled only for the short time a stream still exists before the alarm purges it (this is the same coarse, bounded evidence W8a already leaves for withdrawn rows); after the purge nothing is recorded, so "collect nothing without an approved policy" is preserved.

Checkpoint handling: replay, conflict, stale, tombstones

  • Same (epoch, ckSeq), same digest: idempotent deduplicated ack; merge is monotone so re-applying changes nothing.
  • Same (epoch, ckSeq), different digest: 409, an inconsistent range over the claimed span, nothing else changes; the producer drops the checkpoint and must mint a new epoch.
  • Lower ckSeq or older frontier than already held: accepted as a no-op (merge takes the max); never a downgrade of valid state. ckSeq exists for ack binding and conflict detection, not ordering.
  • Presence failure (a claimed seq is neither delivered nor in a range) ⇒ 409 inconsistent: the producer only claims seqs whose acks it holds, so this means a producer restore, a bug or forgery.
  • Stale / future: observedAt outside [now − dedupe horizon, now + 5 min] ⇒ 422, no taint (a re-signed old checkpoint cannot extend or restore a span). Left edges below revoked_floor, outside the tenant's effective interval or retention window are clipped to nothing, not stored.
  • Tombstones: reuse the existing revoked_floor and dedupe horizon (retention.ts:14); no new tombstone table.

  • Checkpoint txn: validate window, fence and ranges; insert ranges; advance verified_n across newly covered seqs; require accounted.seq ≤ verified_n (presence is the set union of deliveries and ranges, so a seq both delivered and declared lost is fine, and the range still taints); on success merge the span and bump coverage_revision; on failure record an inconsistent range over the claimed span and answer 409.

Chokepoint classification (closes O2) Proposed

prepareTelemetryDelivery is replaced by (or wrapped in) a pure function returning { kind: "delivery", … } | { kind: "unobserved", reason } with reason ∈ {disabled, unprojectable, grant_mismatch, error} for every current return null: disabled = v2 flag off, no collector binding, no grant (not enrolled), invalid coverage setting, or retention policy not in force; unprojectable = unknown source product; grant_mismatch = grade band or source outside the grant; error = the outer catch. The reasons are the same strings as the range enum, so the classification is the range. The Worker passes it to complete() always; the DO ignores it unless a stream already exists (never-enrolled tenants pay nothing and get no table). While a stream exists, an unobserved observation consumes a seq as a range and resets the armed chain. This is what makes "disabled mid-bucket", "invalid setting" and "uninstrumented-by-config" observable whenever there is traffic.

C · Empty, zero-traffic and never-contacted tenants Proposed

Rule: a bucket is verified_zero only if a receiver-held span, produced by an unbroken armed chain, covers its fenced window and accounting is verified, and the stream's commit sequence did not move. A late heartbeat can never extend a chain backwards or across a gap.
Question (brief C)Proposed answer
How is a zero-traffic tenant activated?Two routes, independently shippable. (1) First contact: the first armed completion creates the stream (epoch, t0) and arms the alarm; earlier windows stay unobserved. (2) Cron (optional, Phase 4): a producer scheduled() handler iterates the tenants in HM_TELEMETRY_COVERAGE and calls coverageTick() on each DO (creating it if needed). Cron also acts as a watchdog that re-arms a lost alarm. Both are idempotent.
How do expected intervals and the wakeup schedule become durable?Expected intervals are the receiver's effective-dated coverage.expectedStreams ∩ config intervals ∩ retention window (server-owned, already durable by secret). The wake schedule is the producer alarm: #nextWake() gains "next tick time while armed" and "checkpoint due"; cov_stream persists the chain so a restart resumes the schedule. A cold DO with no state has no obligation and no claim.
What stops it?Approval end, revocation, de-enrolment or invalid setting: the alarm's existing #refreshPolicy false-path withdraws queued rows and (new) purges cov_stream, cov_checkpoint, cov_range, stops ticking and goes idle. Read-time: no checkpoint can be built while the policy is inactive (and the receiver refuses with retention_unapproved). Re-enrolment starts a new epoch, so completeness cannot resume across the lapse.
Unobserved hour vs verified E = 0Both have no rollup row. Only the second has a verified span plus clean accounting. The receiver never writes a zero rollup; the derived read distinguishes them.
Late heartbeatArmed chain restarts (armed_since = now) whenever the previous armed observation is older than maxTickGapSeconds or an off observation intervened. Receiver also requires a span's armedSince ≥ epoch start, ≥ its own config/retention/revocation floor, and consistent with earlier checkpoints of the same chain.
Cost/riskAn armed tenant wakes its DO every tickSeconds (e.g. 96/day at 15 min). Unverified platform cost, cron subrequest limits for large rosters, and alarm reliability. Mitigate by making the tick period a measured parameter and by failing safe (missed ticks only reduce coverage).

F · Retention, expiry and revocation matrix Proposed

Overview, goals and phased tasks

Goals

  • Define exactly what completeness means and prove it for eval_completions.
  • Make unobserved, incomplete, provisional, complete and verified zero distinguishable and durable.
  • Keep v1 and v2 unchanged and default-off; fail closed without approvals.
  • Keep protected transport identities out of analytics; keep retention explicit with no default.

Non-goals

  • Estimating school activity, staffing or service availability.
  • Upstream product submission coverage, reports, cases, reviews (R, I, Q, V, P, C).
  • Dashboards, suppression, differencing limits (W9) or any privacy/legal approval.
  • Deployment, enrolment, issue closure, or any change in this spike.
  • Defending against a compromised producer or a rolled-back receiver.

Risks and mitigations

RiskLevelMitigation
Coverage code in complete() couples analytics failure to moderationHighSTOP 1; fault-injection test V-A6; inert default; keep the hot path to flat SQL with no async work
Fence mis-set causes frequent downgrades (availability) or hides skewMediumMeasure prepare→commit and skew first; fence violations are counted and visible; no default value
Alarm/cron cost and reliability for large rostersMediumTick period is a parameter; missed ticks only reduce coverage; cron is optional (S4)
Receiver migration of dedupe table breaks W7/W8a testsMediumAdditive nullable columns (as W8a did); existing suites unchanged in the gate
Reviewers read "verified zero" as "no activity"HighLabel is "completed evaluations"; rate always null at E = 0; docs replace the unsafe heartbeat sentence (O14)
Verified-zero visibility at 15-minute grain is new disclosureMediumNo read route in S0–S5; W9 review before any exposure

STOP conditions for implementers

  1. Transaction semantics. If the Workers test pool cannot demonstrate that a failing coverage statement either rolls back only the coverage portion (savepoint) or is structurally impossible (single INSERT…SELECT, no constraint that can throw), stop S2. Do not let analytics failure fail the moderation commit, and do not accept partial evidence.
  2. Fence and tick values. Do not choose F, tick or max gap without measured prepare→commit latency and clock-skew data and an operator decision. No defaults in code.
  3. Digest placement. Never move seq inside the digest-bound v2 bytes; digests are async and the frozen-bytes property (O3, O5) must hold.
  4. Read leakage. If any design needs an ack or checkpoint response to carry coverage, counts or watermark, stop: it would turn the writer key into a reader.
  5. Approvals. If implementation needs a retention duration, privacy or legal approval reference, stop and request it. Never invent an approval reference or a default duration.
  6. Unavailable by default. If a change would make completeness anything other than "unavailable" without a verified span, stop.
  7. Heartbeat as evidence. Do not treat receiver health, last-contact time or a producer tick alone as coverage.
  8. Evidence order. If code lets a range or span expire in a way that violates dedupe ≤ rollup ≤ coverage ≤ gap, stop.
  9. Compatibility. Any change to v1/v2 behaviour for a non-coverage tenant, or a failing W8a suite, stops the slice.
  10. Witness. If the receipts witness cannot be verified, do not claim detection of uninstrumented completions; keep rollback below the W8b revision an operational gate.
